## 수정 파일과 안전장치

- `cafeapp/management/commands/apply_taste_scores.py`: JSON 입력안 미리보기와 NULL 필드만 적용하는 관리 명령어.
- `docs/data/taste_scores_2026-09-23.json`: 대상 식별 정보·점수·출처·추정 사유. 값 변경은 이 문서와 함께 재검토한다.
- `cafeapp/test_taste_scores.py`: 기본 미리보기, 백업 필수, 재실행, 기존 점수 보존, 잘못된 값·다른 필드 거절, 식별 불일치 시 중단 검증.
- `.gitignore`: `/backups/taste/`를 제외해 로컬 백업이 실수로 업로드되지 않게 한다.
- 적용 전 전체 Cafe 스냅샷: `backups/taste/before-2026-09-23.json`. 계정·세션 테이블은 포함하지 않는다. 백업 파일이 이미 있으면 덮어쓰지 않고 중단한다.
- DB 변경은 한 트랜잭션에서 처리한다. ID와 이름·국가·도시·주소·대표 메뉴를 대조하고, 운영자 한줄평을 쓴 대상은 해당 문구도 대조한다. 불일치하면 전체 적용 중단.
- 이미 값이 있는 필드는 같은 값이든 다른 값이든 SKIP. 잘못된 기존 값이 있어도 자동으로 고치지 않는다.
- 업데이트는 허용된 맛 필드에만 실행하고, 이후 모든 Cafe 값을 기대 결과와 비교해 다른 값이 변하면 전체 롤백한다.

## 실행 방법

프로젝트 폴더에서 먼저 미리보기:

```powershell
python manage.py apply_taste_scores docs/data/taste_scores_2026-09-23.json
```

실제 적용에는 다음처럼 **새 백업 파일명**을 지정한다. 아래는 로컬에서 이미 완료한 명령이며 재실행하면 두 값은 건너뛴다.

```powershell
python manage.py apply_taste_scores docs/data/taste_scores_2026-09-23.json --apply --backup backups/taste/before-2026-09-23.json
```

운영 서버에는 자동 반영되지 않는다. 서버의 현재 Cafe 목록·대표 메뉴·기존 점수를 따로 확인하고, 서버에서 미리보기를 검토한 뒤 새 백업 경로로 적용해야 한다. 로컬 DB 파일을 서버 DB에 덮어씌우면 안 된다. ID/주소/메뉴가 다르면 입력안을 다시 대조해야 한다.

복구가 필요하면 백업의 두 대상 값을 현재 값과 대조하고 **해당 두 맛 필드만** 되돌린다. 전체 스냅샷을 일괄 복원하면 이후 생긴 정상 변경을 덮어쓸 수 있으므로 자동 전체 복원 기능은 만들지 않았다.

## 검증과 기존 기능 영향

- `python manage.py test cafeapp`: 63개 통과. 루트의 `test_gemini.py`는 실제 유료 API 호출 가능성이 있으므로 자동 발견 대상에서 제외해 실행했다.
- `python manage.py makemigrations --check --dry-run`: 변경 없음.
- 적용 전후 38개 Cafe의 모든 필드를 비교해 2개 셀만 달라진 것을 확인.
- 재실행 미리보기: 두 필드 모두 SKIP, 추가 변경 0개.
- 진하기 필터 결과는 입력한 두 값에 따라 달라질 수 있다. 다른 네 항목을 함께 제한하면 값이 없는 카페는 기존 로직대로 제외된다.
- 현재 취향 추천은 다섯 값이 모두 있는 카페만 대상으로 한다. 이번에는 다섯 값이 완성된 카페가 없으므로 추천 결과를 보장하지 않는다. 이를 해결하려고 임의로 점수를 채우거나 추천 코드를 수정하지 않았다.
