# 말차요정지도 — Coding Rules for Codex

## 1. 가장 중요한 원칙

Codex는 **현재 프로젝트를 먼저 읽고 이해한 뒤 수정한다.**

새로 만드는 것보다 기존 코드를 재사용하는 것을 우선한다.

---

## 2. 작업 시작 전

변경 전 관련 코드를 확인한다. 기능 추가나 여러 파일에 걸친 변경은 아래 항목 중 관련된 내용을 간결하게 요약한다.
문서·오타 등 작은 수정은 목적과 변경 범위만 설명해도 된다. 모든 작업에 전체 목록을 반복하지 않는다.

```text
1. 프로젝트 구조
2. 관련 app
3. 관련 model
4. 관련 view
5. 관련 template
6. 관련 URL
7. 이미 구현된 기능
8. 수정이 필요한 기능
9. 수정 예정 파일
10. migration 필요 여부
```

---

## 3. 단계별 작업

한 번에 전체 프로젝트를 크게 변경하지 않는다.

예:

```text
STEP 1 — 현재 구조 분석
STEP 2 — 데이터 구조 점검
STEP 3 — 검색 / 필터 로직
STEP 4 — 지도 연동
STEP 5 — UI 적용
STEP 6 — 모바일 대응
STEP 7 — 테스트
```

각 단계가 끝난 뒤 결과를 설명한다.

---

## 4. 파일 수정 규칙

- 필요한 파일만 수정한다.
- 전체 파일을 이유 없이 새로 작성하지 않는다.
- 기존 코드를 가능한 한 유지한다.
- 같은 기능을 중복 구현하지 않는다.
- 기존 함수나 클래스 이름을 임의로 바꾸지 않는다.
- URL 이름을 이유 없이 바꾸지 않는다.
- template 경로를 임의로 변경하지 않는다.

---

## 5. 데이터베이스 규칙

모델 변경 전 반드시 설명한다.

다음 형식으로 먼저 알려준다.

```text
변경할 모델:
Cafe

추가할 필드:
country (향후 확장 후보)

필요한 이유:
국가별 카페 탐색이 실제 작업 범위에 포함된 경우

migration:
필요

기존 데이터 영향:
기존 레코드가 있으므로 null/default 검토 필요
```

사용자 확인 없이 기존 데이터를 삭제하지 않는다.

---

## 6. Migration 규칙

migration이 필요하면 명령어까지 알려준다.

예:

```bash
python manage.py makemigrations
python manage.py migrate
```

하지만 migration 파일을 무작정 삭제하거나
DB를 초기화하는 방식으로 문제를 해결하지 않는다.

---

## 7. 라이브러리 추가 규칙

새 패키지를 설치하기 전에 설명한다.

```text
패키지 이름
왜 필요한지
현재 기술로 해결할 수 없는지
requirements.txt 수정 여부
```

기존 라이브러리로 구현할 수 있으면 새 패키지를 추가하지 않는다.

---

## 8. 프론트엔드 규칙

- 기존 Django template 구조를 우선 사용한다.
- 기존 CSS가 있다면 재사용한다.
- JS를 불필요하게 복잡하게 만들지 않는다.
- Leaflet이 이미 있으면 다른 지도 라이브러리로 교체하지 않는다.
- 참고 UI를 그대로 복제하기보다 현재 기능에 맞게 적용한다.
- 모바일 화면도 반드시 확인한다.

---

## 9. 보안 규칙

절대 하지 말 것:

```text
API Key를 코드에 직접 작성
비밀번호를 코드에 작성
.env 값을 Git에 올림
SECRET_KEY를 공개
사용자 입력을 검증 없이 신뢰
```

민감 정보는 환경변수를 사용한다.

---

## 10. Git 친화적인 작업

가능하면 한 단계가 하나의 명확한 변경이 되도록 한다.

예:

```text
feat: add matcha preference filters
fix: sync map markers with search results
style: improve cafe card layout
```

한 번에 너무 많은 목적의 수정을 섞지 않는다.

---

## 11. 금지 사항

### Codex가 임의로 하지 말 것

- 기존 기능 삭제
- 전체 프로젝트 재작성
- DB 초기화
- migration 파일 전체 삭제
- 동작 중인 기능 대규모 리팩터링
- URL 전체 변경
- template 구조 전체 교체
- 사용하지 않는 라이브러리 대량 설치
- 가짜 데이터로 실제 기능인 것처럼 처리
- 실행하지 않은 테스트나 확인을 통과했다고 말하기
- 기존 요구사항 문서를 무시하기

---

## 12. 오류 발생 시

오류를 숨기거나 임시방편으로 넘어가지 않는다.

다음 형식으로 설명한다.

```text
오류:
무슨 오류인지

원인:
왜 발생했는지

수정:
어떤 파일의 어떤 부분을 수정했는지

영향:
다른 기능에 영향이 있는지

확인:
사용자가 어떻게 다시 테스트하면 되는지
```

---

## 13. 작업 완료 후 보고 형식

기능 변경은 아래 항목 중 관련된 내용으로 정리한다. 작은 문서 수정은 변경 요약과 링크 확인 결과 정도로 간결하게 보고한다.

```text
수정한 파일:
- ...

추가한 기능:
- ...

기존 기능 영향:
- 없음 / 있음

DB 변경:
- 없음 / 있음

테스트한 내용:
- ...

사용자가 확인할 방법:
1.
2.
3.
```

---

## 14. 초보 개발자를 위한 설명 규칙

프로젝트 사용자는 비전공자 초보 개발자다.

설명할 때:

- 어려운 용어만 던지지 않는다.
- 한 줄씩 이유를 설명한다.
- "왜 필요한지"를 같이 설명한다.
- 명령어를 줄 때 현재 어떤 폴더에서 실행하는지도 알려준다.
- 위험한 작업은 미리 경고한다.
- 가능한 경우 사람 말 → 코드 순서로 설명한다.

---

## 15. 최종 판단 기준

작업 완료 여부는
"코드가 작성되었는가"가 아니라 다음으로 판단한다.

```text
기존 기능이 깨지지 않았는가?
사용자가 실제로 사용할 수 있는가?
검색/지도/필터가 연결되어 있는가?
모바일에서도 사용할 수 있는가?
향후 확장을 막지 않는가?
사용자가 직접 확인할 수 있는가?
```

## 16. 범위와 검증

- 문서의 미래 기능은 자동으로 구현할 작업 목록이 아니다. 사용자가 요청한 범위에 맞춰 진행한다.
- 일반적인 수정마다 승인을 반복해서 요청하지 않는다. 설명과 승인 요청은 구분한다.
- 기능 변경에는 관련 테스트를 실행하고, UI 변경에는 가능한 범위에서 화면과 모바일 동작을 확인한다.
- 문서만 변경했다면 내용·상대 링크·이미지 경로를 확인한다. 앱 테스트가 불필요한 경우 실행하지 않았다고 명시한다.
- 검증하지 못한 부분과 실제 확인한 내용을 구분한다.
- 이 문서는 개발 원칙이며 현재 보안 설정이 모두 이 원칙을 충족한다는 보증이 아니다.
